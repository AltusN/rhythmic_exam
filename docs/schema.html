Entity relationships

Two islands, not one graph

The five foreign keys form two clusters that never touch. That is not an omission — it is the decision of 2026-08-10 made visible: a practical item asks nothing about a routine beyond an aspect and a score, so it shares no structure with a multiple-choice question. Anything that joins them will live in the exams app, not here.

Island one · practical

Apparatus → Routine → PracticalItem. One routine exists once and four items reference it — one per aspect. Replacing a video changes one row, not four. PROTECT throughout: an apparatus outlives the routines that use it.

Island two · theory

Question → Block, Question → Option → Block. Every word a candidate reads is a block row; legacy's five JSON schemas became this shape. CASCADE throughout: an option has no meaning without its question.

Read this beside the diagram

Four rules no ER diagram draws

pgAdmin builds its canvas from pg_constraint and renders lines for foreign keys. Everything below is real, enforced, and invisible to that process — which is why a generated ERD reads as a simpler design than the one actually running.

index, not constraint

At most one correct option per question

A partial unique index — it constrains only the rows where is_correct is true. Postgres has no partial UNIQUE constraint, so this exists in pg_indexes and not in pg_constraint at all. It gives at most one correct option and never at least one: a question with zero correct options still saves, because there are no child rows for the database to object to. The admin formset closes that half.

CREATE UNIQUE INDEX uq_one_correct_option_per_question
    ON questions_option (question_id) WHERE is_correct;
check

A block's kind must match its payload

One three-armed CHECK on each block table. Exactly one of text, image, video may be non-empty, and it must be the one the kind names. Note it compares against '' rather than NULL — every column in these tables is NOT NULL, so an empty file field is an empty string. One message covers all three arms, which is why a test has to isolate the row it is checking.

CHECK ( (kind='TEXT'  AND text <> '' AND image = '' AND video = '')
     OR (kind='IMAGE' AND image <> '' AND text  = '' AND video = '')
     OR (kind='VIDEO' AND video <> '' AND text  = '' AND image = '') )
timing

Two position rules, checked at different moments

Both block tables defer their (parent, position) uniqueness to COMMIT, so code rewriting positions inside one transaction can swap two of them. Option's equivalent is immediate and fires on every row write. The difference is invisible in any diagram and decides whether a reorder succeeds.

questions_questionblock  UNIQUE (question_id, position)  DEFERRABLE INITIALLY DEFERRED
questions_optionblock    UNIQUE (option_id,   position)  DEFERRABLE INITIALLY DEFERRED
questions_option         UNIQUE (question_id, position)  immediate
not enforced

Aspect is a plain string to Postgres

aspect is varchar(2) with no CHECK and no default. DA, DB, AV and EX are Django TextChoices, enforced by form validation only — a shell, a management command or a fixture load can write ZZ. The uniqueness of (routine_id, aspect) is a real index; the vocabulary is not.

Built by querying pg_attribute, pg_constraint and pg_indexes on the running container, not by reading models.py — so it reflects what the migrations actually created. The test database is built the same way, which is why makemigrations --check earns its place in the suite.

Every column in all seven tables is NOT NULL. Nothing here is exam content: no question text, no options, no expert scores.
