Rhythmic Exam Schema

Sixteen tables, sixteen foreign keys, and a set of rules the database enforces on its own — read straight out of the running Postgres instance.

Entity relationships

Two islands, and the rows that bridge them

The content tables still form two disconnected graphs: a practical one and a theory one. Nothing in questions knows an exam exists. What changed is that exams now reaches into both — and it reaches only through membership rows, never by putting a level or a kind on a question.

Island one · practical

Apparatus → Routine → PracticalItem. One routine exists once and four items reference it — one per aspect. Replacing a video changes one row, not four. PROTECT throughout: an apparatus outlives the routines that use it.

Island two · theory

Question → Block, Question → Option → Block. Every word a candidate reads is a block row; legacy's five JSON schemas became this shape. CASCADE throughout: an option has no meaning without its question.

The bridge · exams

ExamComponent → ComponentQuestion / ComponentPracticalItem. One mechanism for both halves of the exam. Membership is an explicit row, so a question can belong to level 1 and level 2 without being copied — and the copy is what an answer-key correction would otherwise have to chase.

The leaf · sitting

SittingItem → Sitting, and nothing else. A frozen item holds one foreign key. Its component identity is three copied strings and its content is JSON, so no later edit anywhere upstream can reach it. That absence is the point of the table.

Read this beside the diagram

Nine rules no ER diagram draws

pgAdmin builds its canvas from pg_constraint and renders lines for foreign keys. Everything below is real, enforced, and invisible to that process — which is why a generated ERD reads as a simpler design than the one actually running.

index, not constraint

At most one correct option per question

A partial unique index — it constrains only the rows where is_correct is true. Postgres has no partial UNIQUE constraint, so this exists in pg_indexes and not in pg_constraint at all. It gives at most one correct option and never at least one: a question with zero correct options still saves, because there are no child rows for the database to object to. The admin formset closes that half, and so does the freeze, which raises rather than writing an item with no answer key.

CREATE UNIQUE INDEX uq_one_correct_option_per_question
    ON questions_option (question_id) WHERE is_correct;
check

A block's kind must match its payload

One three-armed CHECK on each block table. Exactly one of text, image, video may be non-empty, and it must be the one the kind names. Note it compares against '' rather than NULL — every column in these tables is NOT NULL, so an empty file field is an empty string. One message covers all three arms, which is why a test has to isolate the row it is checking.

CHECK ( (kind='TEXT'  AND text <> '' AND image = '' AND video = '')
     OR (kind='IMAGE' AND image <> '' AND text  = '' AND video = '')
     OR (kind='VIDEO' AND video <> '' AND text  = '' AND image = '') )
timing

Position rules, checked at different moments

Both block tables defer their (parent, position) uniqueness to COMMIT, so code rewriting positions inside one transaction can swap two of them. Every other position rule in the database is immediate and fires on each row write. The difference is invisible in any diagram and decides whether a reorder succeeds.

questions_questionblock  UNIQUE (question_id, position)  DEFERRABLE INITIALLY DEFERRED
questions_optionblock    UNIQUE (option_id,   position)  DEFERRABLE INITIALLY DEFERRED
questions_option         UNIQUE (question_id, position)  immediate
exams_examcomponent      UNIQUE (exam_id,     position)  immediate
exams_componentquestion  UNIQUE (component_id, position) immediate
exams_sittingitem        UNIQUE (sitting_id,  position)  immediate
by omission

The frozen item references nothing

exams_sittingitem carries one foreign key, to its sitting. It does not point at exams_examcomponent, and that is deliberate: grouping items for a component score uses component_name, a copied varchar(50). A foreign key would leave a finished result hostage to a later rename of the live component. The question itself is copied too, into question_snapshot, so the row survives the question being edited or deleted outright.

component_name      varchar(50)   copied, not referenced
component_position  smallint      copied
marking_scheme      varchar(7)    copied
question_snapshot   jsonb         the whole stem and its options
marking_key         jsonb         the answer, kept out of the snapshot
check

One constraint spanning two columns

The only rule in the schema that relates two columns of the same row. A NUMERIC component must carry difference steps and a CHOICE component must carry none — the marking table exists for one and is meaningless for the other. Everything else the database enforces looks at a single column, or at a tuple of columns for uniqueness.

CHECK ( (array_length(difference_steps, 1) > 0 AND marking_scheme = 'NUMERIC')
     OR (array_length(difference_steps, 1) = 0 AND marking_scheme = 'CHOICE') )
by omission

A sitting is the only table with no uniqueness at all

No primary-key-aside constraint of any kind on exams_sitting. That is the fix for a legacy schema which declared UNIQUE (sagf_id) with no year and no attempt number, so one row per person was its ceiling. A judge accumulates sittings across cycles, and retakes the same exam after failing, because nothing forbids either. An absence cannot be seen in a diff, which is why two mutants in the sweep exist only to add the constraints back and confirm the tests object.

gotcha

The empty aspect is a real value

uq_one_component_per_aspect_per_exam has no WHERE clause, so it constrains every row rather than only the ones with an aspect. A theory exam's component carries aspect = '', and '' is a value like any other — so an exam may hold one component with an empty aspect, not several. It is the correct rule for the practical, where the four aspects must be distinct, and a surprise the first time a test tries to build two theory components on one exam.

not enforced

Which vocabularies the database actually knows

Three columns hold a fixed set of strings; two of them are checked and one is not. kind and marking_scheme carry a CHECK naming their values, so a shell or a fixture load cannot write nonsense. aspect carries none in either table that has it — DA, DB, AV, EX are Django TextChoices, enforced by form validation only. The uniqueness of (routine_id, aspect) is a real index; the vocabulary is not.

exams_exam.kind                   CHECK  PRACTICAL | THEORY
exams_examcomponent.marking_scheme CHECK  CHOICE | NUMERIC
exams_examcomponent.aspect        varchar(2)  no check
questions_practicalitem.aspect    varchar(2)  no check
timing

Every foreign key is deferred

Django creates its foreign keys DEFERRABLE INITIALLY DEFERRED on Postgres — all sixteen of them, without anyone choosing it. They are therefore checked at COMMIT, and pytest-django wraps each test in a transaction it rolls back, so commit never arrives. A test asserting that the database refused a dangling reference would pass whether or not it did. The PROTECT tests are unaffected: Django raises ProtectedError in Python before Postgres is consulted.

Built by querying information_schema.columns, pg_constraint and pg_indexes on the running container, not by reading models.py — so it reflects what the migrations actually created. The test database is built the same way, which is why makemigrations --check earns its place in the suite.

Seven columns in the whole schema are nullable. Six of them record something that has not happened yet — three timestamps and a certifier on exams_sitting, a response and a mark on exams_sittingitem — and the seventh is Django's own last_login. Absence is a null here; it is never a zero and never an empty string, which is the one thing the schema this replaces got wrong. Nothing on this page is exam content: no question text, no options, no expert scores.
