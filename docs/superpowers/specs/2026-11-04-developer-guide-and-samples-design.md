# Developer guide and sample data — design

2026-11-04. Brainstormed with Altus; his decisions are marked as his, mine as mine.

## Intent

A developer or sysadmin who has just cloned the repository should, within about an
hour, **sit a practical exam end to end and see it marked**. Knowing where files are
and getting a green test run does not count. They should have watched the system do
its one real job, step by step, and know which function does each step (Altus).

That takes two things that don't exist yet:

1. **Sample data**: an invented practical exam and everything around it, loaded by
   one command.
2. **A developer guide** that goes from clone to setup, then loads the samples, then
   walks through the sitting lifecycle by hand in `manage.py shell`.

## Sequencing

**After the judge-records plan closes**, i.e. after its Task 13 (Altus). That plan is
mid-Task 11, and Task 12 adds enrolment, the review list by candidate number, and
certification to the admin. Those are exactly what the guide tells a newcomer to look
at, so writing the guide before them means writing those sections twice. This slots
in between judge-records and Plan 2 (sign-in).

## Why now

The readme now covers setup (`4407490`), but nothing shows a newcomer what the
system *does*. There is no candidate screen: the only URLs are `/admin/` and the
question preview. The whole lifecycle exists as functions, though, so it can be
driven and observed today.

## Goals

- `manage.py load_samples` (name is my call) creates a complete, invented
  practical exam setup on an empty database.
- The guide walks through `enrol` → `start_sitting` → `record_response` ×20 →
  `submit_sitting` → reading the results → optionally `certify`, by hand in the
  shell. After each step it says what to look at, either a query or an admin page,
  and what should have changed (Altus: learning the lifecycle beats a command that
  plays the candidate).
- A reset path a newcomer can use to start again.

## Non-goals

- **A user guide for judges or officials.** That comes later. The official's admin
  part waits for Task 11 and certification to land; the candidate part waits for
  the exam screen to exist (agreed with Altus).
- Theory sample data. Theory decides nothing; it can be added later as a second
  sample.
- A command that plays the candidate automatically.
- A tour of every model.

## Anti-goals

- **Anything resembling real exam content.** The repository is public. No real
  questions, expert scores, routines or media, and nothing trimmed down from
  `rhytmic*.db`. Every value is invented.
- **Sample data that could be mistaken for real.** Every name says it is sample
  data, such as "Sample practical" and "sample rope". The marking table and expert
  scores are invented and must never be treated as SAGF's real tables (open
  question 1 in `CLAUDE.md`).
- **A custom reset command.** See Reset below.
- **Committed binary media.** Placeholder videos are generated by the command, not
  checked in.

## Constraints

- **Altus writes the command and its test** (his decision; code and tests are his
  per `CLAUDE.md`). Claude writes the guide and this design, and reviews and
  mutates the command as usual. Tests are shown red before they are accepted.
- **A management command, not a JSON fixture** (Altus). It builds through the
  models, so it survives schema changes better than a fixture of fixed pks, and
  the constraints get exercised along the way.
- **Refuse unless the database is empty** (Altus). Samples load only on an empty
  database, and "already loaded" is one case of "not empty".
  - *Empty* means no rows in any table of our own apps: `questions`, `exams` and
    `accounts`, excluding Django's own tables. A superuser created to log into the
    admin does not count, so `createsuperuser` before `load_samples` works. **This
    definition is my call.** `accounts.User` is our model, so the check excludes
    the user table. That is enough: `User` has no history table, and nothing in our
    apps creates a row when a user is created (checked by the builder review).
  - It refuses with a message saying what it found and pointing at the reset path.
    It does not partially load.
- **Refuse unless `DEBUG` is true** (Altus, 2026-11-04). The emptiness check describes
  the data, not the environment, and a freshly migrated production database is
  empty too. Without this guard, the command run during a real deployment's setup
  would put a fake exam and fake judges on a live roster. `settings.py` defaults
  `DEBUG` to false, so a deployment that forgets to set it is refused as well. It
  has its own test and its own mutant.
- **All-or-nothing**: the whole load runs in one `transaction.atomic()`, so a crash
  halfway never leaves a half-seeded database that the emptiness check then
  refuses.
- `Decimal` for every score and boundary, never `float`.

## What the samples contain

The exact values are left to the builder, except where stated.

- **Apparatus**: `Rope, Hoop, Ball, Clubs, Ribbon`, positions 1–5, FIG order. This
  part is real, and safe, per `CLAUDE.md`.
- **Five routines**, one per apparatus, each with a generated placeholder video
  file under `MEDIA_ROOT`. `Routine.video` is a required `FileField`. A few bytes
  is fine, because nothing plays it in the walkthrough.
- **One practical exam**: level and year are invented, and the year must fall
  inside the sample cycle. It has four components, `DA`, `DB`, `AV` and `EX`, in
  that order. Each component has five items (one per routine) with invented expert
  scores, a marking table and grade bands.
- **Grade bands**: use the evaluation scale already published in the design spec
  (Difficulty bands for `DA`/`DB`, Artistry/Execution for `AV`/`EX`). It is the FIG
  rule, already public, and it makes the grades meaningful. Band names must match
  what the category requirements name.
- **Marking table**: invented, and labelled as such in the guide.
- **A cycle** containing the exam year, with the §2.6 category requirements from
  the design spec.
- **Two or three judges**: a `User`, `JudgeProfile` and `RosterEntry` for the exam
  year whose levels let them enrol in the sample exam. Ideally one has a reason to
  be refused (wrong level, or not on the roster), so the guide can show a refusal
  and an override. That is my suggestion, and the builder can drop it.

## Reset

**No reset command** (agreed with Altus after this argument, which is derived):

- Removing *only the samples* isn't one step once someone has done the
  walkthrough. By then there are sittings, items, results, maybe a certification,
  and history rows. FKs into `Sitting` cascade and `Apparatus` is `PROTECT`ed, so a
  selective teardown either grows with every new model or cascades further than
  intended.
- On a real deployment, a `reset` command is one mistyped command away from
  deleting candidates' records. That is the deletion the admin lock on `Sitting`
  (Task 10) exists to prevent.
- Django already provides the wipe: `manage.py flush`. The harder version is
  `docker compose down -v`, then `docker compose up -d` and `migrate`.

The guide documents reset as `flush` followed by `load_samples`.

## The guide

`docs/developer-guide.md`, linked from the readme (location is my call). **Claude
writes and commits it** (Altus, 2026-11-04). It is prose about the code, like the
readme, not code.

1. **Setup**: point at the readme rather than repeat it, plus `createsuperuser`.
2. **Load the samples**, then what to look at in the admin: the exam, its
   components and their tables.
3. **Sit the exam in the shell.** For each step: the call, what it does in one
   line, what to look at afterwards, and which finding it closes where that
   applies. F1/F2 at the freeze (edit a marking table after `start_sitting` and
   watch the mark ignore it), F3/F4 at marking (enter an unreadable answer), F5 at
   the component percentage.
4. **Read the result**: `ComponentResult` per aspect, then the examination category
   via `exams/awards.py`.
5. **Certify** (optional): `certify` with the superuser as the official.
6. **Reset**: `flush`, then `load_samples`.
7. **Where to go next**: the spec, the decisions log, the mutation sweep.

The guide must be run, not just written. Every snippet gets executed against a
freshly loaded database before the guide is committed, and the output it shows is
real output.

## Testing

Altus writes it, red first:

- The command on an empty database creates the expected rows. Assert the shape as
  literals (counts per model, the component order, the apparatus order), not just
  "something exists". Inputs should disagree with whatever order a mutation would
  produce, per `CLAUDE.md`.
- The command refuses on a non-empty database and writes nothing. Assert the table
  contents, not `count()` alone.
- The command does not count the superuser as data.
- A failure partway leaves nothing behind. Whether this needs its own test or is
  pinned by a mutant of the `atomic()` line is left to the review round.
- **An end-to-end walkthrough test** (agreed with Altus, 2026-11-04). It runs
  `load_samples`, then the guide's calls: enrol a sample judge, start the sitting,
  twenty responses, submit. Then it asserts the four `ComponentResult` rows as
  `(aspect, percentage, grade_name)` literals and the examination category as a
  literal.
  - **It makes a different claim from Task 9's end-to-end test.** That one builds
    its own exam from `conftest.py` and proves the *code* works. This one proves
    the *samples* can be sat. Its mutant: a sample judge's roster level one below
    the exam's. The load succeeds and every count is right, but `enrol` refuses.
    Band names that don't match the category requirements, and an expert score
    outside its marking table, belong to the same family.
  - **The responses land on different grades**, e.g. `DA` Excellent and `EX` Good,
    so that the weakest aspect visibly caps the category. All-correct answers give
    100% and Category 1 for many wrong setups, including samples attached to the
    wrong component.
  - **The guide uses the same twenty responses**, so the numbers it prints are the
    test's literals.
  - Constructs: `call_command("load_samples")`, and pytest-django's `settings`
    fixture for `DEBUG = True` and `MEDIA_ROOT = tmp_path`.

Mutants for the command go into `tools/mutation_sweep.py` (Claude, as usual).

## Placement and order

```
rhythmic/exams/management/commands/load_samples.py   the command
rhythmic/tests/exams/test_load_samples.py            what it creates, when it refuses
rhythmic/tests/exams/test_samples_walkthrough.py     the end-to-end walkthrough
```

`exams` holds the command because it is at the top of the import graph: it already
imports from `accounts` and `questions`, and neither imports from `exams`. Two test
files, because they make two different claims.

Order: the command's tests, then the command (Altus); then the walkthrough test
(Altus); then the guide (Claude), which copies its numbers from that test.

## Left to the builder

- The command's name, file layout and output messages.
- Keeping media generated by the command's tests out of the real `MEDIA_ROOT`
  (`settings.MEDIA_ROOT` overridden to a temporary directory). `rhythmic/media/`
  is gitignored either way.
- How the guide shows output that varies between runs, such as the random
  `candidate_number` and timestamps (an elided value or a placeholder is fine).
- The exact invented values: expert scores, marking table steps, level and year,
  and judge names. They must be invented and look invented.
- How the placeholder video is generated.
- Whether one sample judge demonstrates a refusal.
