# Django Skeleton Implementation Plan

> **Tutoring mode — this plan deviates from the standard format.**
> Altus writes every line of test and application code. Claude explains concepts,
> reviews what is written, and pushes back — Claude does not implement.
>
> **This plan shows more concrete material than the scoring plan did, deliberately.**
> The split is by category, not by convenience:
>
> | Category | Who produces it | Why |
> |---|---|---|
> | `django-admin startproject` output | generated — run the command | Same class as migrations. Typing it teaches nothing. |
> | `ruff.toml`, `compose.yaml`, `.env`, settings blocks | shown in this plan | Configuration. The learning is in understanding each key, not recalling its spelling. |
> | Tests | **Altus writes** | Test design is the skill being built. Cases and expected values are given; the code is not. |
> | Any Python that makes a decision | **Altus writes** | Unchanged from the scoring plan. |

**Goal:** A Django project that boots, talks to Postgres in a container, and proves
both with tests — before any model, view or app exists.

**Architecture:** One Django project (`config/`) living beside the existing
framework-free `scoring/` package inside `rhythmic/`. Settings read from the
environment. Postgres runs in Docker Compose; Django runs on the host against it.
`pytest` remains the single test runner, extended with `pytest-django`.

**Tech Stack:** Python 3.12, Django >= 6.1, psycopg 3, python-dotenv,
pytest-django, Docker Compose, Postgres 17.

## Global Constraints

- **`rhythmic/scoring/` still imports nothing from Django and touches no database.**
  Task 1 changes *where* that rule is enforced, never whether it is.
- **No secret is ever committed.** `SECRET_KEY` and database credentials come from
  the environment. `.env` is already covered by `.gitignore:16` (`.*env`) —
  verified with `git check-ignore` on 2026-08-05.
- **`Decimal` everywhere for marks and deductions, never `float`.** Unchanged.
- **Check `git status` before committing.** `git commit` commits the whole index.
- **Commit messages follow Conventional Commits.** Scope for this plan is
  `config` for project-level work; omit the scope when the change is repo-wide.
- **Run ruff and pytest from `rhythmic/`.** The pre-commit hook does the same and
  will block a commit that is not clean.

## Why the skeleton is its own plan

The questions app is where the interesting decisions are — content blocks, papers,
the F9 level rule. None of them can be reasoned about while `DATABASES` is still
throwing. Splitting means the unfamiliar mechanics (settings, compose, how Django
tests run) get their own review gates, and the questions plan gets written *after*
`manage.py` is a familiar tool rather than before.

## Where this lives

Everything is inside `rhythmic/`, and **every path and command below is relative to
that directory** unless it says otherwise. Start with `cd rhythmic`.

**The `git` steps are the exception and run from the repository root**, because
their paths are shown root-relative (`rhythmic/config/...`, `.env.example`). Git
resolves pathspecs against your current directory, so running them from `rhythmic/`
looks for `rhythmic/rhythmic/config/...` and fails.

`compose.yaml` also lives at the repository root, because Docker is a
repository-level concern and the eventual application image will need `legacy/`
excluded and `docs/` ignored.

**So do `.env` and `.env.example`, and there is exactly one of each.** Compose reads
`.env` from its own directory, which is the root; Django reaches up for it with
`load_dotenv(BASE_DIR.parent / ".env")`. The database password has to reach both the
container and the application, and keeping two copies in step by hand is how you
lose twenty minutes to a connection refusal that is really a typo. `BASE_DIR` comes
from `__file__`, so `.parent` holds regardless of which directory you run from.

## Deviation from the spec, stated deliberately

The spec's Operations section says `compose.yaml` carries "application plus
Postgres". **This plan ships Postgres only.** Containerising the application needs a
Dockerfile, a WSGI server and a static-file story, for an application that currently
has no views. That is deployment work, and it belongs with the first thing worth
deploying. Django runs on the host against the containerised database, which is the
normal development posture anyway and still teaches compose, volumes and networking.

Recorded here so a later reader sees a decision rather than an omission.

### Task 1: Scope the framework ban to `scoring/`

**Files:**
- Create: `scoring/ruff.toml`
- Modify: `pyproject.toml` — remove the `[tool.ruff.lint.flake8-tidy-imports.banned-api]` table

**Why this is first:** the ban currently lives in `rhythmic/pyproject.toml` and
therefore applies to **everything** under `rhythmic/`, despite its message saying
"scoring/". Verified on 2026-08-05: a file at `rhythmic/_djangocheck.py` containing
`from django.db import models` raises
`TID251 django is banned: scoring/ is framework-free`. Your first Django file would
be blocked by the pre-commit hook. Nothing else in this plan can be committed until
this is fixed.

**The mechanism:** ruff resolves the *nearest* configuration file for each file it
checks. A `ruff.toml` inside `scoring/` therefore governs `scoring/` alone. `extend`
pulls in the parent so the rule set (`E W F I UP C4 B TID RET BLE SIM`, `E501`
ignored) is inherited rather than replaced — verified: `RET` and `BLE` still resolve
for `scoring/` files after the move.

- [ ] **Step 1: Write `scoring/ruff.toml`**

```toml
# The framework ban lives here, not in ../pyproject.toml, so that it applies to
# scoring/ and nothing else. Ruff resolves the nearest config per file.
#
# `extend` inherits the parent's rule selection; without it this file would
# replace the selection rather than add to it.
extend = "../pyproject.toml"

[lint.flake8-tidy-imports.banned-api]
"django".msg = "scoring/ is framework-free; if a module needs Django, the boundary is wrong"
"sqlalchemy".msg = "scoring/ touches no database; marking tables arrive as arguments"
"flask".msg = "Flask lives in legacy/ only; new code imports no web framework"
```

Note the table header is `[lint...]`, not `[tool.ruff.lint...]`. A standalone
`ruff.toml` has no `[tool.ruff]` prefix; a `pyproject.toml` does. Getting this wrong
fails silently — the table is simply ignored and the ban disappears.

- [ ] **Step 2: Remove the same table from `pyproject.toml`**

Delete these four lines (the comment above them explains the ordering constraint and
goes too, since the table it warns about is leaving):

```toml
# Sub-tables must stay last: a TOML table header claims every key below it
# until the next header, so any bare key here would leave [tool.ruff.lint].
[tool.ruff.lint.flake8-tidy-imports.banned-api]
"django".msg = "..."
"sqlalchemy".msg = "..."
"flask".msg = "..."
```

- [ ] **Step 3: Prove the ban moved rather than vanished**

Two throwaway files, one either side of the boundary:

```bash
printf 'from django.db import models\n\nprint(models)\n' > _outside.py
printf 'from django.db import models\n\nprint(models)\n' > scoring/_inside.py
../.venv/bin/ruff check _outside.py scoring/_inside.py
rm _outside.py scoring/_inside.py
```

Expected: `_outside.py` clean, `scoring/_inside.py` reports `TID251`. If **both**
are clean the ban has been lost, which is the failure that matters — it is silent,
and it would let a Django import into `scoring/` months from now.

- [ ] **Step 4: Confirm `scoring/` still inherits the parent rule set**

```bash
../.venv/bin/ruff check . && ../.venv/bin/ruff format --check . && ../.venv/bin/python -m pytest -q
```

Expected: clean, clean, **81 passed**. If `RET` or `BLE` findings appear that were
not there before, `extend` is not resolving and `scoring/` is being linted under
ruff's defaults.

- [ ] **Step 5: Commit**

```bash
git status --short
git add rhythmic/scoring/ruff.toml rhythmic/pyproject.toml
git commit
```

Subject: `chore(scoring): scope the framework ban to the scoring package`
Body: the ban applied to all of `rhythmic/` and would have blocked the first Django
file; nearest-config-per-file scopes it, `extend` keeps the rule set.

**Review gate:** Claude checks that the ban genuinely still fires inside `scoring/`

> **Corrected 2026-08-08.** This task originally committed the `SECRET_KEY` that
> `startproject` generates and left Task 3 to replace it. That was wrong: this
> repository is public, and a value committed once is in history permanently
> regardless of what a later commit does. Removing it afterwards would mean

**Why a `web` extra rather than `dependencies`:** the distribution declared by this

### Task 4: Postgres in Compose, and the first migration

**Files:**
- Create: `compose.yaml` (repository root, **not** inside `rhythmic/`)

**The concept.** Compose describes containers declaratively. One service here:
Postgres, with a named volume so data survives `docker compose down`, and a port
published to the host so Django — running on the host — can reach it at
`127.0.0.1:5432`. `POSTGRES_*` variables configure the official image on first
start; Compose reads the repository-root `.env` automatically, which is why the
same names are used on both sides.

- [ ] **Step 1: Write `compose.yaml`**

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  pgdata:
```

Three things worth understanding rather than copying:

- `"127.0.0.1:5432:5432"` binds to loopback only. Plain `"5432:5432"` binds to every
  interface, which on a laptop on a café network means an internet-reachable
  database. Docker publishes ports *past* most host firewalls, so this is not
  theoretical.
- `$$` in the healthcheck escapes Compose's own variable substitution so the shell
  inside the container expands it instead.
- The named volume `pgdata` is why your data survives a restart. Removing it —
  `docker compose down -v` — is how you deliberately start clean.

- [ ] **Step 2: Confirm Compose is reading the values it needs**

Nothing to create — the `POSTGRES_*` keys went into the single root `.env` in
Task 3, which is the directory Compose reads from. Verify the substitution resolves
before starting anything:

```bash

```

Expected: the rendered configuration with real values in place of `${POSTGRES_DB}`
and friends. An empty value or a warning about an unset variable means `.env` is in

Expected: the `db` service listed as `healthy`. If it is `starting` for more than a

### Task 5: Prove the stack boots, with tests

**Files:**
- Modify: `pyproject.toml` — add `[tool.pytest.ini_options]`
- Create: `tests/test_django_smoke.py`

**Why this task exists.** Everything so far was verified by running commands by
hand. A command you ran once is not a guarantee; the point of this task is that
`pytest` alone will tell you the stack is intact, forever.

**The concept.** `pytest-django` needs to know which settings module to use, and
`config` must be importable. Both go in `pyproject.toml`. Tests that touch the
database must be marked — `pytest-django` gives each marked test a transaction that
is rolled back afterwards, so tests never see each other's data. Unmarked tests are
*blocked* from database access, which is why your 81 scoring tests will keep passing
untouched and will keep proving that `scoring/` needs no database.

- [ ] **Step 1: Configure pytest**

In `pyproject.toml`:

```toml
[tool.pytest.ini_options]
DJANGO_SETTINGS_MODULE = "config.settings"
pythonpath = ["."]
```

`pythonpath = ["."]` is the part that will bite you if omitted. `rhythmic-scoring`
is installed editable but declares `packages = ["scoring"]`, so `config` is not on
`sys.path` by virtue of the install. Without this line you get
`ModuleNotFoundError: No module named 'config'` at collection — which, as you know
from Tasks 4 and 5 of the scoring plan, takes the whole suite down rather than
failing one test.

- [ ] **Step 2: Write the failing tests**

Two of them, in `tests/test_django_smoke.py`. You write these; here is exactly what
each must establish and nothing more:

| Test | What it does | Expected |
|---|---|---|
| `test_admin_login_page_renders` | `django.test.Client` GET on `/admin/login/` | status `200` |
| `test_database_is_reachable` | marked `@pytest.mark.django_db`; count the rows in Django's own `Session` model | `0`, and no exception |

The first proves settings, URL routing and middleware are wired without needing a
database. The second proves Postgres is genuinely reachable and that migrations ran
— a `Session` table that does not exist raises rather than returning zero.

Use `django.test.Client`, imported inside the test module. `from django.contrib.
sessions.models import Session` gives you the model for the second.

- [ ] **Step 3: Run them and watch them fail**

```bash
../.venv/bin/python -m pytest tests/test_django_smoke.py -v
```

Expected before Step 1 is applied: a collection error on `config`. With Step 1
applied but Postgres stopped: `test_database_is_reachable` fails with a connection
error while `test_admin_login_page_renders` passes — which is itself worth seeing,
because it shows the two tests really do check different things.

- [ ] **Step 4: Run the whole suite**

```bash
docker compose -f ../compose.yaml up -d
../.venv/bin/python -m pytest -q
```

Expected: **83 passed** — the 81 scoring tests plus these two. If the scoring tests
have slowed noticeably, something is giving them database access they should not have.

- [ ] **Step 5: Confirm the boundary still holds**

```bash
../.venv/bin/ruff check . && ../.venv/bin/ruff format --check .
```

Expected: clean. Task 1's ban is still the thing keeping `scoring/` framework-free,
